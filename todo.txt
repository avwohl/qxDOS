  the shader one is worth recording because the first assessment of it was too
pessimistic.  it looked architectural: v0.83.0's
gui/render/private/shader_common.h:14 includes "glad/gl.h" with no C_OPENGL
guard, private/shader.h:17 declares `GLuint program_object', and
gui/render/shader_manager.cpp called glDeleteProgram and
Shader::BuildShaderProgram with no guard at all while shader.cpp's whole body
sits behind `#if C_OPENGL'.  the conclusion drawn was that those symbols were
unresolvable with C_OPENGL=0 no matter what, and that the way out was either
enabling OpenGL or patching render.cpp and sdl_gui.cpp.
  neither was needed.  glad's gl.h is 4865 lines with ZERO inline bodies and 983
extern function-pointer declarations, so including it costs nothing at link -
only CALLING a gl function does.  and shader_manager.cpp turned out to have
exactly one such call.  so: add ${DB}/libs/glad/release/include to the include
path for the types, and guard the one call and the one BuildShaderProgram use
behind #if C_OPENGL.  two hunks.  render.cpp and sdl_gui.cpp are untouched, no
file was dropped from the build, and glad's gl.c is still not compiled because
nothing references a pointer from it.
  WHAT IS ACTUALLY LEFT: a build.  every claim above is static - paths resolve,
patches apply with no fuzz, declared symbols match their headers, no unguarded GL
call remains in any compiled translation unit.  none of it is a compiler's
opinion.  four thousand commits of upstream drift across 241 files will contain
things this kind of checking cannot see: changed semantics behind unchanged
signatures, template instantiation failures, ODR problems, anything to do with
the Objective-C++ side.  the next step is `cmake --build' on a Mac, and the
useful thing to record afterwards is what static analysis MISSED, because that

- the x87 DELIVERS its exceptions as of 2026-08-28, and this entry is what is
left of that one: the transcendentals below, plus a correction and one new
thing the work uncovered.  the delivery itself is in CHANGELOG.md.
  THE CLAIM THIS ENTRY USED TO MAKE WAS WRONG and is worth leaving visible:
it said "in practice DOS software masks - DJGPP's startup does - which is why
this has never been the thing that broke".  DJGPP 2.02+ does mask, and so does
Watcom, but BORLAND DOES NOT - its DOS runtimes leave invalid-operation,
divide-by-zero and overflow unmasked by default, which is what Turbo Pascal's
runtime errors 205, 206 and 207 are built on.  that is a large population of
real-mode software, and the reason the IRQ13 path was worth building rather
than stopping at CR0.NE.
  the machine used to contradict itself about whether it HAD a coprocessor,
and that closed on 2026-08-29, the owner having asked for it.  the BDA
equipment word at 40:10 was built without bit 1 (0x0025) while CMOS 0x14 said
the opposite (0x2F, bit 1 set), and INT 11h returns the BDA word verbatim - so
a guest probing the documented way was told there was no x87, chose its
software emulator, and never executed an x87 instruction at all.  emu88 has
always emulated a complete 80-bit x87 whatever config.cpu says, so "absent" was
the lie.  three sources agree now: the equipment word (bit 1 set, default reads
0x0027), CPUID leaf 1 EDX bit 0, and DPMI INT 31h AX=0E00h, which used to
report 8001h "unsupported function" and now answers 0x31 - present, no
emulation, type 3 - which is the value dosiz has always given.  CR0.ET and
CR0.MP are set at POST in the same pass, as a real POST does on finding a
coprocessor.
  ONE CONSEQUENCE IS WORTH KNOWING and is not a defect: CR0.MP is what makes
WAIT honour CR0.TS, so WAIT can now raise #NM where it never could before.
Nothing in this machine reaches it - CR0.TS is set in exactly one place,
emu88_pmode.cc's task switch, and neither the BIOS nor the DPMI host performs
one - and the same #NM has always been raised by any ESC instruction with TS
set, so this is a new trigger rather than a new failure class.  Measured, with
TS forced and vector 7 left on an IRET stub that clears nothing: 999 dispatches
and then raise_exception's loop detector halts the CPU, rather than hanging.  A
guest doing lazy FPU switching would have a #NM handler and would clear TS with
CLTS, which is the case the bit exists for.
  one latent bug is recorded rather than fixed, because nothing reaches it
today: dos_machine.cc's hardware-IRQ loop runs irq 0..15 against a uint8_t
pic_imr, so `pic_imr & (1 << irq)` is always 0 for irq >= 8 - those can never
be masked - and it dispatches `pic_vector_base + irq`, which for irq 13 is
INT 15h rather than the AT's INT 75h.  it is unreachable only because the sole
producer is the Sound Blaster with a default irq of 5 and nothing validates a
configured sb_irq; an sb_irq of 8 would set the video mode from the audio
thread.  the coprocessor latch deliberately does not use that loop.
  the transcendentals are the other half of the same entry, and it grew on
2026-08-28.  they are accurate to a worst observed 4 ulp of a 64-bit
significand (tests/f80_unit.cc prints a worst case per function and holds the
set to a bound of 6; FSINCOS is not listed separately because it is the same
code path as FSIN and FCOS), which
is about what an 80387 delivers and some 500x better than the host-double
implementation they replaced, but they
are not correctly rounded and neither suite pretends they are.  a spot check
against an exact reference showed part of the remaining difference is glibc's
rather than ours, so the number is an upper bound on our error, not a
measurement of it.

- emu88's trace and debug hooks are a whole unused extension point, and this is
the one piece of dead scaffolding the 2026-08-27 sweep deliberately did NOT
delete.  emu88/emu88_trace.h declares a 27-line abstract class with four virtual
hooks (comment, asm_op, flush, fetch); emu88.h holds an `emu88_trace *trace' and
a public virtual set_trace(); emu88.cc defines a `static emu88_trace
dummy_trace' and initialises the member to it.  `grep -rn 'trace->\|set_trace'
over emu88/, tests/, qxDOS/ and dosiz/src/ returns one hit, the declaration of
set_trace itself: nothing calls a hook and nothing installs a tracer.  The
`bool debug' beside it is the same - set false in the constructor, exposed
through set_debug(), never read.  Unlike the counters and the empty bodies that
were deleted that day, this is a coherent designed seam rather than a leftover:
somebody meant a disassembler to plug in here.  It is dead either way, and
removing a public virtual from a class a second product compiles is a decision
somebody should make on purpose.

- the pre-992c7fc detect-only AdLib timer and Sound Blaster DSP stubs are still
in dos_machine.cc's port switch, reachable when config.sound_card == 0.  a guest
configured with no sound card therefore "detects" an AdLib at 0x388 and a DSP at
0x220 that produce nothing, which is worse than not detecting at all - a game
that finds an AdLib configures itself for FM music and then plays none.  no
harness covers that configuration.  docs/hardware-roadmap.md records it on both
the AdLib and the Sound Blaster row.  deleting the stubs is the obvious fix and
was NOT done here: it changes what a shipping configuration reports to a guest,
and nothing on this machine can run the shipping configuration.
