x86_64 box with g++ (Ubuntu 15.2.0-16ubuntu1) 15.2.0, no clang, no Xcode, and

  the scope: SingleStepTests as run here is REAL MODE ONLY.  sst386.cc loads
  every segment register through cpu.load_segment_real for all 1.76M cases -
  grep load_segment_real in tests/sst386.cc, the comment there is "base =
  sel<<4, limit 0xFFFF".  the corpus directory is named v1_ex_real_mode and the
  unreal/protected/virtual directories tests/data/80386/README.md says will
  eventually exist do not.  so 99.9831% is a statement about real-mode
  per-instruction behaviour and nothing else.  it also never scores exception
  DELIVERY: the corpus injects a HALT at the ISR entry, so a fault is graded by
  the registers and RAM it leaves, never by whether the right vector was
  dispatched with the right frame.  32-bit protected-mode execution - where
  every DJGPP and PMODE/W client runs - is covered only by test386's one
  full-system pass, which is a check of the machinery rather than per-
  instruction coverage.  the IDIV bug 7352fc5 fixed lived in exactly that gap
  and was invisible for as long as both suites existed.

- CI runs the suites now, and what it does NOT cover is the thing to keep in
view.  .github/workflows/tests.yml builds all seven harnesses and runs
tests/run_suites.sh on every push and pull request, with the ~600MB corpora
cached; run_suites.sh holds SingleStepTests to 1758402/1758699 and diffs
test386's arithmetic output against the reference, which is the check that was
missing.  It was shown to fail before it was trusted: against a core built from
before 7352fc5 it still reports "ok reached POST 0xFF" and then fails the diff,
which is exactly how the IDIV bug hid.
  What that does not buy: SingleStepTests as run is real mode only, and the
corpus injects a HALT at the exception ISRs, so 32-bit protected-mode
instruction execution and exception delivery are still covered only by
test386's full-system pass - a check of the machinery, not of every
instruction.  Automating a suite does not widen it.  The release workflow is
still the only other thing in .github/workflows/ and still touches neither
emu88/ nor tests/.

- the DPMI host and NE2000 are compiled into every harness and executed by none
of them.  grep -lniE 'dpmi|ne2000|int ?21|dos_bios' over tests/*.cc returns
nothing at all, yet build.sh's DOS variable links emu88/dos_dpmi.cc,
emu88/dos_bios.cc and emu88/ne2000.cc into vesa_test and hardware_test - so
1727 lines of dos_dpmi.cc, 2196 of dos_bios.cc and 425 of ne2000.cc are
compile-checked and never run past whatever the INT 10h VESA path in
vesa_test.cc happens to reach.  DPMI protected-mode execution is the same gap
the IDIV bug lived in, and it is the mode the product's users are in.

- emu88's x87 FPU has zero automated coverage: 870 lines in emu88_fpu.cc that
neither suite touches a single instruction of.  none of the 941 opcode files in
tests/data/80386/v1_ex_real_mode begins D8..DF - the capture bench was an Intel
80386EX, which has no FPU, per tests/data/80386/README.md - and test386.asm
does not exercise it either, since the mnemonic column of
test386-EE-reference.txt is 96 distinct entries with no x87 mnemonic among
them. emu88_fpu.cc itself carries acknowledged shortcuts: grep "stub" in it for
FLDENV and FNSTENV. against that, README.md advertises "Full 386 CPU with FPU
and DPMI support" and docs/hardware-roadmap.md marks FPU done.  both rest on
nothing measured. note that the FPU is not idle in practice - FUCOMPP was one
of the four fixes adopted from dosiz in e89af9c, found because GCC emits it for
long-double comparisons.

straight out of this working tree, and nothing gates a change to them.

emu88_fpu.cc, emu88_mem.cc, opl.cc and sound_blaster.cc.  not a submodule, not
a vendored copy, not a pinned SHA - a relative path into a sibling checkout,
with no version constant, no checksum and no build stamp.  dosiz/CLAUDE.md says
which way the obligation runs: "emu88 belongs to qxDOS.  Do not fix emu88 bugs
from this repo", and points at qxDOS/tests/ as the gate.  grepping this repo
for the word dosiz finds three incidental code comments (emu88/audio_device.h,
emu88/dos_machine.h, docs/hardware-roadmap.md) and, in CHANGELOG.md, two
entries recording fixes that came the other way (:146, :162).  nothing in
README.md, CLAUDE.md or tests/README.md names the dependency at all, and
nothing anywhere states the obligation as a rule.  so a commit here lands in
dosiz's
next `make` silently. the coverage runs the wrong way round, too: this repo
owns the suites and they are real-mode-per-instruction plus one ROM, while
dosiz owns roughly thirty protected-mode DPMI fixtures in its ci.yml
(DPMI_STAGE4/5/5_32/6, DPMI_RMCB, DPMI_DESCMGMT, DPMI_PMIDT, EMS/VCPI probes, a

gate is the real work.

- dosiz's CI could not configure, was confirmed and fixed on 2026-08-27, and
what is left is the asymmetry.  It is not "probably" any more: a fresh clone
plus `make` reproduced the FATAL_ERROR exactly as predicted, and dosiz eeefe79
now checks this repository out into its workspace and passes EMU88_DIR
explicitly, pinned at a full 40-character SHA (a short one is taken for a branch
name by actions/checkout, which failed the first dispatched run).  That job is
green.
  So a commit here can no longer break dosiz's BUILD without someone seeing a
red tick - but nothing tells dosiz that emu88's BEHAVIOUR moved, and nothing
here knows dosiz pins us.  The pin lives in dosiz's workflow only; this repo
carries no record of which of its own commits a downstream is on, and no CI job
here builds dosiz.  Bumping that pin stays a deliberate act on their side, which
is the intent, but it means a fix made here reaches them only when they ask for
it.

- emu88_mem::store_mem carries four dead debug blocks on the path taken by
every guest byte write, and that path is shared with dosiz.  grep
watchpoint_addr in emu88/emu88_mem.cc: a three-way range compare whose body is
`{ }`. below it, an IVT[21h] block commented "temp debug" that reads
dat[masked], sets ivt21_trap = true and then executes a bare `;`.  grep
ivt21_trap across emu88/ returns exactly two hits - that write and its
declaration in emu88_mem.h - so nothing anywhere reads the flag.  below that,
two blocks marked "temporary debug" over the DPMI LDT range
0x00FE2860..0x00FE6800 and the GDT range 0x00FE0000..0x00FE2000, whose bodies
now only increment a static counter that fed a print that was deleted. every
store pays the compares. the cost was not measured, and that is the argument
for deleting them rather than a reason to keep them.

- an 80-entry LDT dump runs on every intercepted #NP and feeds a print that no
longer exists: 640 fetch_mem calls to decide whether to execute a bare `;`.  in
emu88/dos_dpmi.cc, inside the `if (dpmi.exc_installed[vector])` block, `if
(vector == 0x0B)` loops e from 0 to 79 reading eight bytes each through
mem->fetch_mem, ORs all eight together and runs an empty statement.  ad01cd0's
own closing paragraph flagged it - "One is not free: an LDT dump on every
intercepted #NP still costs 640 memory reads.  Worth a separate sweep." - and
no commit since has touched it.  #NP is the segment-not-present path a DPMI
client takes routinely.
