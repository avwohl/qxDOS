- emu88's x87 register stack is host double, not 80-bit extended, and nothing
the product says admits it.  emu88.h:184 declares `double regs[8]' - 53
mantissa bits against a 387's 64 - so a whole class of results is not
reproducible here and will not be without a rewrite.  tests/fpu_test.cc pins 31
of those divergences exactly rather than leaving them implicit, measured
2026-08-27: FLD m80real of 1+2^-53 collapses to 1.0, there is no denormal
class, no stack-overflow detection, precision control is ignored entirely,
FLDENV/FNSTENV are control-word-and-status-word stubs, and F2XM1 is pow(2,x)-1
and FYL2XP1 is log2(x+1), so both lose exactly the precision those instructions
exist to preserve.  against that, README.md advertises "Full 386 CPU with FPU
and DPMI support" and docs/hardware-roadmap.md marks FPU done.
  the zero-coverage half of this entry closed the same day - 437 assertions
over ~74 mnemonics, driven as real opcode bytes through the decoder - but
coverage does not widen the format.  neither suite could have found this:
none of the 941 opcode files in tests/data/80386/v1_ex_real_mode begins D8..DF,
because the capture bench was an Intel 80386EX with no FPU per
tests/data/80386/README.md, and the mnemonic column of
test386-EE-reference.txt is 96 distinct entries with no x87 mnemonic among
them.  the FPU is not idle in practice - FUCOMPP was one of the four fixes
adopted from dosiz in e89af9c, found because GCC emits it for long-double
comparisons.

- thirteen emu88 defects are recorded by the two new harnesses and none of them
is fixed.  tests/fpu_test.cc holds nine and tests/dpmi_test.cc four, each as a
bug() assertion stating the architecturally correct answer, held to a
KNOWN_BUGS_EXPECTED baseline the way run_suites.sh holds SingleStepTests to
SST_BASELINE - so fixing one turns the harness red and says to lower the
number, rather than going quietly green.  tests/README.md sections 4 and 5
describe each one.  measured 2026-08-27 against f265310.
  two of them are worth doing first, both in the DPMI host and both reachable
by any ordinary client.  emu88/dos_dpmi.cc case 0x0002 checks its seg_map
cache and then runs `break', which leaves the enclosing for loop rather than
the switch case, so the allocate-a-new-descriptor path below runs anyway: every
repeat lookup of one real-mode segment burns another LDT entry, and DJGPP's
__dpmi_segment_to_descriptor called in a loop walks through all 2047.  the fix
is `return' and the harness goes green on it with no other edit.  and
dpmi_reflect_to_rm computes rm_sp = stack_top & 0x0F, which is 0 for every
512-byte-aligned level, so the first push wraps SP to FFFEh and every reflected
real-mode interrupt lands its frame at physical 171FAh - 64KB above the
7000h-8000h locked stack the comment says is reserved for it, which in a real
session is the DOS kernel, a driver, or the client's own image.
  the remaining eleven are smaller: a process-global callback counter that
0304h never reclaims, 0400h advertising virtual memory this host has no paging
for, and nine x87 conformance defects of which FCOMI leaving OF/SF/AF untouched
is the one a compiled program is most likely to notice - guest code that does
FCOMI and branches JL/JLE/JG/JGE reads whatever the last integer instruction
left behind.
  fixing any of them is a change to a file dosiz compiles out of this tree, so
it reaches them on their next pin bump.  that is the argument for doing it
deliberately rather than as a drive-by, and it is why nothing here is fixed
yet.

- neither new harness reaches everything, and tests/README.md says where.

test there tests the compiler.  DD C8-CF and DE D8+i for i != 1 are undefined
