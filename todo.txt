- the v0.83.0 bump is statically clean and has never been compiled.  twelve
build breaks were found by audit and all twelve are closed - the six lost fork
patches recovered into dosbox-ios/patches/, the two renamed webserver classes,
the MidiSynth reparenting in the fluidsynth stub, three newly-required upstream
sources, DOSBOX_VERSION_SHORT, the obsolete imgmount_fix.cpp, and the shader

run a compiler over it.
  the shader one is worth recording because the first assessment of it was too
pessimistic.  it looked architectural: v0.83.0's
gui/render/private/shader_common.h:14 includes "glad/gl.h" with no C_OPENGL
guard, private/shader.h:17 declares `GLuint program_object', and
gui/render/shader_manager.cpp called glDeleteProgram and
Shader::BuildShaderProgram with no guard at all while shader.cpp's whole body
sits behind `#if C_OPENGL'.  the conclusion drawn was that those symbols were
unresolvable with C_OPENGL=0 no matter what, and that the way out was either
enabling OpenGL or patching render.cpp and sdl_gui.cpp.
  neither was needed.  glad's gl.h is 4865 lines with ZERO inline bodies and 983
extern function-pointer declarations, so including it costs nothing at link -
only CALLING a gl function does.  and shader_manager.cpp turned out to have
exactly one such call.  so: add ${DB}/libs/glad/release/include to the include
path for the types, and guard the one call and the one BuildShaderProgram use
behind #if C_OPENGL.  two hunks.  render.cpp and sdl_gui.cpp are untouched, no
file was dropped from the build, and glad's gl.c is still not compiled because
nothing references a pointer from it.
  WHAT IS ACTUALLY LEFT: a build.  every claim above is static - paths resolve,
patches apply with no fuzz, declared symbols match their headers, no unguarded GL
call remains in any compiled translation unit.  none of it is a compiler's
opinion.  four thousand commits of upstream drift across 241 files will contain
things this kind of checking cannot see: changed semantics behind unchanged
signatures, template instantiation failures, ODR problems, anything to do with
the Objective-C++ side.  the next step is `cmake --build' on a Mac, and the
useful thing to record afterwards is what static analysis MISSED, because that
is the number that says how much to trust this method next time.

  the scope: SingleStepTests as run here is REAL MODE ONLY.  sst386.cc loads
  every segment register through cpu.load_segment_real for all 1.76M cases -
  grep load_segment_real in tests/sst386.cc, the comment there is "base =
  sel<<4, limit 0xFFFF".  the corpus directory is named v1_ex_real_mode and the
  unreal/protected/virtual directories tests/data/80386/README.md says will
  eventually exist do not.  so 99.9831% is a statement about real-mode
  per-instruction behaviour and nothing else.  it also never scores exception
  DELIVERY: the corpus injects a HALT at the ISR entry, so a fault is graded by
  the registers and RAM it leaves, never by whether the right vector was
  dispatched with the right frame.  32-bit protected-mode execution - where
  every DJGPP and PMODE/W client runs - is covered only by test386's one
  full-system pass, which is a check of the machinery rather than per-
  instruction coverage.  the IDIV bug 7352fc5 fixed lived in exactly that gap
  and was invisible for as long as both suites existed.
  the four harnesses added since - fpu, dpmi, ne2000, bios - narrow the gap and
  do not close it.  three of the four drive a real-mode machine; dpmi_test is
  the only one that runs protected-mode code, and it runs the DPMI host's own,
  not a corpus.

- the x87 raises exceptions and does not DELIVER them.  the 80-bit register
file landed on 2026-08-28 and is in CHANGELOG.md; what it did not bring is
#MF.  emu88_fpu.cc now latches ES and B in the status word when a raised
exception is not masked, so a program that polls FNSTSW sees it, but there is
no vector 16 dispatch, no FERR pin, and CR0.NE is declared in emu88.h:70 and
read nowhere.  a guest that UNMASKS an exception and waits for a trap waits
forever.  in practice DOS software masks - DJGPP's startup does - which is why
this has never been the thing that broke, and it is recorded rather than fixed
because delivery needs an IRQ13 path and a decision about CR0.NE that nothing
currently forces.
  the transcendentals are the other half of the same entry, and it grew on
2026-08-28.  they are accurate to a worst observed 4 ulp of a 64-bit
significand (tests/f80_unit.cc prints a worst case per function and holds the
set to a bound of 6; FSINCOS is not listed separately because it is the same
code path as FSIN and FCOS), which
is about what an 80387 delivers and some 500x better than the host-double
implementation they replaced, but they
are not correctly rounded and neither suite pretends they are.  a spot check
against an exact reference showed part of the remaining difference is glibc's
rather than ours, so the number is an upper bound on our error, not a
measurement of it.

- fifteen or so x87 defects are reported and NOT fixed, and this entry exists
so they are written down somewhere other than a chat log.  a differential hunt
against the host x87 on 2026-08-28 produced 39 distinct findings; twelve were
fixed in two passes (f5f8f18 and the commit after it) and each of those twelve
was reproduced against the host by hand before being touched.  what is below is
the rest.
  THESE WERE RE-VERIFIED ON 2026-08-28 AND ALL OF THEM REPRODUCE.  An earlier
version of this entry warned that up to seven were probably not defects,
because the hunt that found them returned 7 refutations it did not attach to
particular findings.  That warning was wrong and is corrected here rather than
deleted: a second pass built a probe per finding against the host x87 and
confirmed every one at high confidence, with none refuted and none already
fixed by accident.  The 7 refutations must have landed on findings that were
fixed while the run was still going.
  Two of them came back with the REPORT corrected rather than just confirmed,
which is worth knowing before picking one up.  The two unmasked-exception
entries are ONE change, not two: whether #P belongs on an unmasked overflow
depends on the inexactness of the 24576-biased value, so the flags cannot be
fixed without computing that value.  And the fix proposed for it - "do not set
#P for an unmasked overflow" - is wrong as stated; it breaks the 82 of 738
cases in that verifier's own sweep where the biased result really is inexact.

  what is LEFT of the transcendental exception family, three of whose four
  counts closed on 2026-08-28 and are in CHANGELOG.md.  rounding control
  reaches all eight now, an overflowing FYL2X reports #O, and an exact FYL2X no
  longer reports a #P it did not earn.  two things did not close:
    - #U for a tiny result.  F2XM1 of 2^-16382 reports #P where the host
      reports #U|#P.  that underflow happens in an INTERMEDIATE multiply which
      has already been denormalised in a throwaway context by the time the last
      step runs, so moving the final rounding into the caller's context - which
      is what fixed the other three - cannot see it.  fixing it means carrying
      underflow information out of the intermediates, which is a different and
      larger change.
    - C1.  it is derived from a real rounding now rather than being hard zero,
      but its agreement with hardware is unchanged at about chance (measured
      2365/4000 after against 2010/4000 before, at RC=nearest), because it
      depends on which way OUR approximation rounds and ours sits a couple of
      ulp from the host's.  closing this properly needs the transcendentals to
      be correctly rounded, which is a much bigger claim than the 6-ulp bound
      they are held to.

  the rest, each with the file it is in:
  - emu88_f80.h: unmasked #O and #U deliver the MASKED result rather than the
    value with the exponent biased by -/+24576.  nothing here delivers #MF
    either, so this only matters to a guest that unmasks and polls.
  - emu88_f80.h: f80_round_pack ignores the exception masks - an exact tiny
    result raises no #U when #U is unmasked, and an unmasked #O also sets #P.
  - emu88_f80.h: an m32/m64 SNaN operand is quieted BEFORE the NaN-selection
    rule runs, so the wrong NaN can win.
  - emu88_f80.h: FPREM/FPREM1 hand back a pseudo-denormal dividend in its
    unnormalized encoding.
  - emu88_fpu.cc: FLDENV/FRSTOR take the three non-EMPTY tag encodings
    verbatim.  a real x87 keeps only the EMPTY/non-EMPTY decision from the
    image and re-derives valid/zero/special from what is actually in the
    register - so an image whose tag word disagrees with its register data
    round-trips differently here than on hardware.  note the FRSTOR case
    currently documents taking them verbatim as DELIBERATE, so that comment is
    part of what has to change.
  - emu88_fpu.cc: the 32-bit environment images leave the reserved upper halves
    zero where a real x87 writes all ones.
  - emu88_fpu.cc: when one instruction both reads an empty register AND pushes
    onto a full stack, C1 reports the overflow where hardware reports the first
    fault, the underflow.

- emu88's trace and debug hooks are a whole unused extension point, and this is
the one piece of dead scaffolding the 2026-08-27 sweep deliberately did NOT
delete.  emu88/emu88_trace.h declares a 27-line abstract class with four virtual
hooks (comment, asm_op, flush, fetch); emu88.h holds an `emu88_trace *trace' and
a public virtual set_trace(); emu88.cc defines a `static emu88_trace
dummy_trace' and initialises the member to it.  `grep -rn 'trace->\|set_trace'
over emu88/, tests/, qxDOS/ and dosiz/src/ returns one hit, the declaration of
set_trace itself: nothing calls a hook and nothing installs a tracer.  The
`bool debug' beside it is the same - set false in the constructor, exposed
through set_debug(), never read.  Unlike the counters and the empty bodies that
were deleted that day, this is a coherent designed seam rather than a leftover:
somebody meant a disassembler to plug in here.  It is dead either way, and
removing a public virtual from a class a second product compiles is a decision
somebody should make on purpose.

- the pre-992c7fc detect-only AdLib timer and Sound Blaster DSP stubs are still
in dos_machine.cc's port switch, reachable when config.sound_card == 0.  a guest
configured with no sound card therefore "detects" an AdLib at 0x388 and a DSP at
0x220 that produce nothing, which is worse than not detecting at all - a game
that finds an AdLib configures itself for FM music and then plays none.  no
harness covers that configuration.  docs/hardware-roadmap.md records it on both
the AdLib and the Sound Blaster row.  deleting the stubs is the obvious fix and
was NOT done here: it changes what a shipping configuration reports to a guest,
and nothing on this machine can run the shipping configuration.
