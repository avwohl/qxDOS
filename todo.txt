    src/gui/render/private/shader_common.h:14 does `#include "glad/gl.h"' with
      NO C_OPENGL guard.  five compiled translation units reach it transitively -
      gui/render/render.cpp, gui/render/shader_manager.cpp,
      gui/render/auto_image_adjustments.cpp, gui/sdl_gui.cpp and the patched
      gui/render/sdl_renderer.cpp.  glad exists upstream at src/libs/glad, but
      `grep -n glad dosbox-ios/CMakeLists.txt' returns NOTHING - it is not on the
      include path, because this build has never needed it.
    src/gui/render/shader_manager.cpp contains ZERO occurrences of C_OPENGL and
      calls glDeleteProgram at :114 and Shader::BuildShaderProgram at :184.
      glDeleteProgram is a glad function pointer defined only in glad's gl.c,
      which upstream compiles only when C_OPENGL is on.  BuildShaderProgram is
      defined in src/gui/render/shader.cpp, whose entire body sits behind
      `#if C_OPENGL' at line 6.
    this build sets C_OPENGL 0, at dosbox_config.h:52 and as a compile definition
      at CMakeLists.txt:570.
  so with C_OPENGL=0 those two symbols are unresolvable NO MATTER WHAT is added
to the source list.  upstream made the shader path assume OpenGL is present and
this build assumes it is not.  three options, none mechanical:
    turn C_OPENGL on and vendor glad.  the largest change, and it runs against
      the grain of the platform: the app renders through SDL's Metal backend and
      OpenGL ES is deprecated on Apple platforms.
    stop compiling shader_manager.cpp and auto_image_adjustments.cpp and patch
      render.cpp and sdl_gui.cpp not to need them.  fits the patch mechanism
      dosbox-ios/patches/ already provides and is the most in keeping with what
      this integration does, but it is a real patch against churning upstream
      code, not a one-liner.
    add glad's include directory and gl.c so the header resolves and the function
      pointers link.  NOT sufficient alone: BuildShaderProgram still does not
      exist with C_OPENGL=0.
  whoever picks one needs a Mac.  eleven breaks were found without building; the
twelfth is where a compiler has to be involved, and where the count of remaining
ones stops being knowable from here.

- emu88's x87 register stack is host double, not 80-bit extended, and that is a
rewrite rather than a defect.  emu88.h declares `double regs[8]' - 53 mantissa
bits against a 387's 64 - so a whole class of results is not reproducible here.
tests/fpu_test.cc pins 31 of those divergences exactly rather than leaving them
implicit: FLD m80real of 1+2^-53 collapses to 1.0, there is no denormal class,
no stack-overflow detection, precision control is ignored entirely,
FLDENV/FNSTENV are control-word-and-status-word stubs, and F2XM1 is pow(2,x)-1
and FYL2XP1 is log2(x+1), so both lose exactly the precision those instructions
exist to preserve.
  the nine conformance defects that were NOT explained by the double design are
fixed as of 2026-08-27 and are in CHANGELOG.md.  the format is not.  fixing it
means an 80-bit soft-float register file and every arithmetic path rewritten
against it.  the harness that would grade the result exists now, which it did
not before, but neither validation suite can help: none of the 941 opcode files
in tests/data/80386/v1_ex_real_mode begins D8..DF, because the capture bench was
an Intel 80386EX with no FPU per tests/data/80386/README.md, and the mnemonic
column of test386-EE-reference.txt is 96 distinct entries with no x87 mnemonic
among them.  the FPU is not idle in practice - FUCOMPP was one of the four fixes
adopted from dosiz in e89af9c, found because GCC emits it for long-double
comparisons.
  README.md and docs/hardware-roadmap.md both say this now, in those words,
rather than advertising "Full 386 CPU with FPU".

- emu88's trace and debug hooks are a whole unused extension point, and this is
the one piece of dead scaffolding the 2026-08-27 sweep deliberately did NOT
delete.  emu88/emu88_trace.h declares a 27-line abstract class with four virtual
hooks (comment, asm_op, flush, fetch); emu88.h holds an `emu88_trace *trace' and
a public virtual set_trace(); emu88.cc defines a `static emu88_trace
dummy_trace' and initialises the member to it.  `grep -rn 'trace->\|set_trace'
over emu88/, tests/, qxDOS/ and dosiz/src/ returns one hit, the declaration of
set_trace itself: nothing calls a hook and nothing installs a tracer.  The
`bool debug' beside it is the same - set false in the constructor, exposed
through set_debug(), never read.  Unlike the counters and the empty bodies that
were deleted that day, this is a coherent designed seam rather than a leftover:
somebody meant a disassembler to plug in here.  It is dead either way, and
removing a public virtual from a class a second product compiles is a decision
somebody should make on purpose.

- the pre-992c7fc detect-only AdLib timer and Sound Blaster DSP stubs are still
in dos_machine.cc's port switch, reachable when config.sound_card == 0.  a guest
configured with no sound card therefore "detects" an AdLib at 0x388 and a DSP at
0x220 that produce nothing, which is worse than not detecting at all - a game
that finds an AdLib configures itself for FM music and then plays none.  no
harness covers that configuration.  docs/hardware-roadmap.md records it on both
the AdLib and the Sound Blaster row.  deleting the stubs is the obvious fix and
was NOT done here: it changes what a shipping configuration reports to a guest,
and nothing on this machine can run the shipping configuration.
